## D-001｜2026-09-27｜管理号锁定语义采用快照单模式（snapshot）

**问题**：需求 3.1「生成后锁定」与十三「改字段不改号」矛盾——号内字段（会场/落札日期/进货价）改不改、号变不变。

**论证**：
- 方案 A（快照单模式）：号内字段可改、管理号恒不变，号内各段是生成时快照列，允许与现值分歧（详情页显示分歧徽标）。符合十三字面；单一路径，校验/测试/错误码/文档单一。
- 方案 B（严格锁定）：号内字段一改即 409，引导作废重录。符合 3.1 字面；但录错一个字符就要作废重录（拍照/图片全部重来），高频路径体验差。
- 方案 C（双模式开关 lock_policy）：默认快照、可切严格。覆盖两种口径；但最高频改动路径的校验/测试/错误码/文档 ×2，且开关大概率永远停在默认值=永久维护的死代码。

**决策**：方案 A。需求十三是需求文档自己的异常裁决节，是对 3.1 含糊单元格的权威解释；作废重录保留为纠错路径（错价场景推荐）。

**影响面**：item 表快照列设计、PUT /items 校验逻辑、详情页分歧徽标、测试用例。

**推翻条件**：甲方确认单回复「号内字段不允许修改」，回补严格模式为半天级有界增量（单模式实现是严格模式的子集）。

## D-002｜2026-09-27｜价格码默认进编号（include_price_code=true）

**问题**：需求 4.1 示例（HTK9-A1X 含 X）与 4.2 文字（「不进编号」）矛盾。

**论证**：以例为准（示例是最具体的表达，且 4.2 的「不进编号」与其自身「月份、价格档位保留在编号中」句直接矛盾）；做成 application.yml 属性而非运行时开关——对外业务格式（买家可见+CSV 匹配依赖），切换属发版级变更不该由管理员随手点。

**决策**：默认含价格码；yml 属性 `itemcode.include-price-code=true`，M2 甲方确认后固化。

**影响面**：CodeFormatUtil、正则、Excel 旧号导入解析。

**推翻条件**：甲方答「不含」——改一处 yml+重跑测试即切换，生成器已参数化。

## D-003｜2026-09-27｜年份代号种子 2016=A、不跳 I/O

**问题**：需求示例 2026=K/2027=L 隐含的字母序列起点与是否跳过 I/O 未明说。

**论证**：2026 是字母表第 11 个字母 K ⇒ 从 A 数起 2016=A；若跳 I/O 则 2026=L 与示例矛盾。不跳 I/O 与需求示例自洽。

**决策**：种子数据 2016=A 逐年排到 2041=Z，不跳 I/O。

**影响面**：year_code 种子数据；编号中不出现具体年份数字的需求已满足。

**推翻条件**：甲方提供真实历史对照表与推算不符——替换种子数据即可，无代码改动。

## D-004｜2026-09-27｜实时同步保留 SSE（30s 轮询为已评估备选）

**问题**：实时同步用 SSE 长连接还是简单轮询。SSE 规格经多轮加固（登出关连接/401 防风暴/visibilitychange 重建/nginx 五件套/12h 超时/池 16），实现与维护成本高于轮询。

**论证**：
- SSE：需求一显式承诺「多人同时操作实时一致」；亚秒级跨端新鲜度；单向通知场景 SSE 是最轻量长连接方案（Spring 原生 SseEmitter）。成本：nginx 配置段+前端重连状态机+约 6 条专项测试。
- 30s 轮询：实现减半；但「刚卖出的货对方 30s 内还能再卖」在两人对讲机协作的现场作业里有真实窗口期风险，且 10 用户×每 30s 全量查询的负载与 SSE 心跳相当。

**决策**：SSE 保留。切换轮询是纯增量（前端 useSse 换实现，后端保留失效事件源）。

**影响面**：7.6 全节、nginx 配置、useSse。

**推翻条件**：甲方对「实时」口径确认接受 30s 延迟——前端换轮询实现，半天级。

## D-005｜2026-09-27｜iOS 后台补传不做推送子系统，四件套兜底

**问题**：iOS 无后台执行（Web Push 不能拉起业务 JS），图片补传延迟如何兜。

**论证**：Web Push+setAppBadge+PeriodicBackgroundSync 四件推送组件的到达率链条=「装了主屏+授了通知权+恰好关着 app+有存图」每环衰减；而照片已在 Dexie 持久化（主屏安装豁免 7 天 ITP 清储，WebKit 官方行为）——数据永不丢，仅上传延迟。推送子系统（VAPID 密钥/订阅存储/权限链）复杂度与收益不成比例。

**决策**：四件套兜底=打开即补传+页内角标 N+pagehide「N 张未传完」警示+主屏安装引导；安卓一次性 Background Sync 为主路径。

**影响面**：7.5 触发矩阵、PWA 引导流程。

**推翻条件**：甲方反馈现场常出现「整日不打开 app 且急需照片即时上传」场景——回补 Web Push 为独立增量（不影响既有架构）。

## D-006｜2026-09-27｜二维码生成唯一实现=前端 qrcode 库

**问题**：二维码在录入成功页（离线可用）、打印页、单件重打三处需要，服务端 ZXing 还是前端生成。

**论证**：录入成功页要求离线可用 ⇒ 前端生成是刚需；三处共用同一实现防「码内容」口径分叉；服务端 ZXing 只为打印页多一条服务端路径+一个 Maven 依赖，无独立价值。浏览器打印若个别打印机对不齐，PDF 服务端兜底是半天级纯增量。

**决策**：前端 qrcode 1.5 全站唯一实现；QR 规格（ECC=M/quiet zone≥4/模块≥0.5mm/码边≥14mm/300DPI）固化。

**影响面**：7.7、打印页、录入成功页。

**推翻条件**：甲方特定打印机实测浏览器打印对不齐——加 PDF 兜底端点。

## D-007｜2026-09-27｜运行时配置开关收敛 11→3

**问题**：多轮评审曾累计 11 个 sys_setting 运行时开关（锁定策略/图片鉴权/导出字段/SSE 降级/上传配额等）。

**论证**：开关越多=测试矩阵组合爆炸+「开关永远停在默认值」的死代码越多；逐项评估：滞销 N/M 与标签尺寸有需求明文（保留 admin UI）；CSV 列映射放 yml（格式变更本需发版验证，给非技术甲方的 JSON 编辑框是陷阱）；登录阈值/图片上限无运营调参场景（常量）；其余均砍（需要时均为小改增量）。

**决策**：sys_setting 仅存滞销 N/M+标签尺寸；include_price_code=yml。

**影响面**：5.3、setting 模块、admin UI。

**推翻条件**：甲方提出明确的运行时调参需求——单项加回均为独立小改。

## D-008｜2026-09-27｜MySQL 容器 buffer_pool 384M（非 512M）

**问题**：测试服务器 768M cgroup 限额下 MySQL 内存配置。

**论证**：512M 池+performance_schema 150-300M+基础 RSS 120-180M≈800M-1GB，超 768M 硬限=OOM 重启循环（「零影响隔离」变「零影响但自杀」）；数据集封顶 ~400MB、热集 ~10MB，384M 覆盖 >95% 场景，性能损失≈0；关 performance-schema（无监控抓取链路）。

**决策**：`--performance-schema=OFF` + innodb_buffer_pool_size=384M，常驻 ~550-600M。

**影响面**：deploy compose、压测环境同值。

**推翻条件**：压测 p95 不达标且 profiling 证明瓶颈在 buffer pool——评估单独 MySQL 宿主/升配。

## D-009｜2026-09-27｜对账不变量采用「双向入账」公式

**问题**：ledger 与 item 现状如何自检（TRANSFER 记 0、在途退货、作废三类行在朴素公式下数学不成立）。

**论证**：每行按 (from仓,−move)/(to仓,+move) 双向入账后，每仓 Σ入账 ≡ COUNT(在库未删未废) 对全部 14 类 txn 成立；VOID/回收站删除按库存态钉死记账（在库 −1、在途/已出库 0）。

**决策**：双向入账公式+每日自检 job（按仓聚合首遍扫+命中下钻）+结果落 sys_alert。

**影响面**：LedgerWriter、每日 job、restore --verify 复用。

**推翻条件**：新增 ledger 类型时重新验证公式覆盖（进 code-review 清单）。

## D-010｜2026-09-27｜测试策略采用确定性场景矩阵（弃 jqwik/随机混沌）

**问题**：CSV 合并不变量与并发容错的测试形态——property-based 随机生成还是枚举矩阵。

**论证**：输入空间（状态×价格×时间戳序）可枚举——枚举矩阵失败必可复现；jqwik 随机失败需还原种子、CI flaky 治理成本高；并发混沌（随机 kill 连接/重启容器）同理，Testcontainers 无 restart() 一等 API。

**决策**：CSV 三不变量枚举矩阵；并发容错=DataSource 代理 5 注入点参数化故障注入；容器重启降级为 M7 手动演练留档。

**影响面**：十一节测试表。

**推翻条件**：无（纯测试形态决策，成本已锁定）。

## D-011｜2026-09-27｜「出荷待ち」独立业务入口（不并入对账视图）

**问题**：已成交未出库的商品清单放在哪。

**论证**：雅虎成交→打款→打包发货有数天时滞，这是仓库每天的拣货队列（日课），不是对账异常；埋在 reconcile 命名空间里=每天打开「异常页」干正常活。

**决策**：移动+桌面双入口「出荷待ち」清单（按货架号排序+缩略图+行内扫码卖出）；对账三活视图保留同一差集作滞留监控视角。

**影响面**：六节 API、前端页面。

**推翻条件**：甲方反馈发货时滞实际很短——两视图合并为小改。

## D-012｜2026-09-27｜作废重录前后件互链（re_entry_of 列）

**问题**：作废重录后，扫旧标签如何找到新号（否则盘点时新旧对不上，全靠认照片翻录入记录）。

**论证**：无互链=物理标签与系统脱节，盘点差异人工裁决成本高；互链仅一列+remark 自动互写，成本极低。

**决策**：item.re_entry_of BIGINT UNSIGNED NULL；作废弹层提示「撕除/划掉旧标签」。

**影响面**：5.1 DDL、作废流程、扫码提示。

**推翻条件**：无。

## D-013｜2026-09-27｜覆盖率门禁：BUNDLE ≥60% + 核心域行 ≥85%/分支 ≥70%

**问题**：全局 80% 无 enforcement+核心 70% 的旧口径=最高风险模块拿最低门槛。

**论证**：风险与门槛应同向——itemcode/inventory/yahoo 是账实正确性与并发的所在，行 85%/分支 70%；其余（DTO/entity/config 排除后）BUNDLE 60% 防形式主义；mapper XML 由集成测试承担（口径显式声明）；前端 stores/composables/utils ≥80%（纯 TS 零 DOM，ROI 最高）。

**决策**：JaCoCo 分域门禁（lombok.config 加 @Generated 过滤）+vitest coverage threshold 入 CI。

**影响面**：CI、十节。

**推翻条件**：无。

## D-014｜2026-09-27｜单 SPA 双 shell（非双应用）

**问题**：移动 Vant / 桌面 Element Plus 两套 UI 的组织形态。

**论证**：双应用=两份构建/两套路由/两份 i18n 同步维护；单 SPA 双 shell=路由级分包（Vant 与 EP 互不加载）+共享 stores/composables，代码单源。风险=chunk 渗漏与样式交叉，用纪律约束（共享组件禁用两库组件、弹层不跨 shell）。

**决策**：单 SPA 双 shell，UA 自动选+手动切换。

**影响面**：前端整体结构。

**推翻条件**：构建产物证明双库无法有效分包（互相拉入对方 chunk）——拆双应用，stores 层可平移。

## D-015｜2026-09-27｜测试环境仅录虚构数据（APPI 合规）

**问题**：测试环境部署在中国境内服务器，员工真实商品照片/操作日志属 APPI 个人关联数据。

**论证**：真实数据存中国境内构成跨境传输；测试数据无真实价值（不迁移生产）；seeder 造数脚本与压测共用一举两得。

**决策**：测试环境仅虚构数据，造数脚本复用压测 seeder。

**影响面**：M7 演练流程。

**推翻条件**：无（合规保守方向）。
