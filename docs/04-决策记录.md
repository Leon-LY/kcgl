## D-001｜2026-09-27｜管理号锁定语义采用快照单模式（snapshot）

**问题**：需求 3.1「生成后锁定」与十三「改字段不改号」矛盾——号内字段（会场/落札日期/进货价）改不改、号变不变。

**论证**：
- 方案 A（快照单模式）：号内字段可改、管理号恒不变，号内各段是生成时快照列，允许与现值分歧（详情页显示分歧徽标）。符合十三字面；单一路径，校验/测试/错误码/文档单一。
- 方案 B（严格锁定）：号内字段一改即 409，引导作废重录。符合 3.1 字面；但录错一个字符就要作废重录（拍照/图片全部重来），高频路径体验差。
- 方案 C（双模式开关 lock_policy）：默认快照、可切严格。覆盖两种口径；但最高频改动路径的校验/测试/错误码/文档 ×2，且开关大概率永远停在默认值=永久维护的死代码。

**决策**：方案 A。需求十三是需求文档自己的异常裁决节，是对 3.1 含糊单元格的权威解释；作废重录保留为纠错路径（错价场景推荐）。

**影响面**：item 表快照列设计、PUT /items 校验逻辑、详情页分歧徽标、测试用例。

**推翻条件**：甲方确认单回复「号内字段不允许修改」，回补严格模式为半天级有界增量（单模式实现是严格模式的子集）。

## D-002｜2026-09-27｜价格码默认进编号（include_price_code=true）　→ 已获甲方确认

**问题**：需求 4.1 示例（HTK9-A1X 含 X）与 4.2 文字（「不进编号」）矛盾。

**论证**：以例为准（示例是最具体的表达，且 4.2 的「不进编号」与其自身「月份、价格档位保留在编号中」句直接矛盾）；做成 application.yml 属性而非运行时开关——对外业务格式（买家可见+CSV 匹配依赖），切换属发版级变更不该由管理员随手点。

**影响面**：CodeFormatUtil、正则、Excel 旧号导入解析。

**推翻条件**：甲方答「不含」——改一处 yml+重跑测试即切换，生成器已参数化。

**✅ 确认记录（2026-09-27）**：甲方答复「价格档位要进编号」——D-002 转为最终口径，`include_price_code=true` 固化，不再作为可切属性跟踪（yml 参数化保留作部署级安全网）。同批答复：价格档位对照表由用户在后台页面自行设置（原 A3 问题消解，无需甲方交付数据）。

## D-003｜2026-09-27｜年份代号种子 2016=A、不跳 I/O

**问题**：需求示例 2026=K/2027=L 隐含的字母序列起点与是否跳过 I/O 未明说。

**论证**：2026 是字母表第 11 个字母 K ⇒ 从 A 数起 2016=A；若跳 I/O 则 2026=L 与示例矛盾。不跳 I/O 与需求示例自洽。

**决策**：种子数据 2016=A 逐年排到 2041=Z，不跳 I/O。

**影响面**：year_code 种子数据；编号中不出现具体年份数字的需求已满足。

**推翻条件**：甲方提供真实历史对照表与推算不符——替换种子数据即可，无代码改动。

## D-004｜2026-09-27｜实时同步保留 SSE（30s 轮询为已评估备选）

**问题**：实时同步用 SSE 长连接还是简单轮询。SSE 规格经多轮加固（登出关连接/401 防风暴/visibilitychange 重建/nginx 五件套/12h 超时/池 16），实现与维护成本高于轮询。

**论证**：
- SSE：需求一显式承诺「多人同时操作实时一致」；亚秒级跨端新鲜度；单向通知场景 SSE 是最轻量长连接方案（Spring 原生 SseEmitter）。成本：nginx 配置段+前端重连状态机+约 6 条专项测试。
- 30s 轮询：实现减半；但「刚卖出的货对方 30s 内还能再卖」在两人对讲机协作的现场作业里有真实窗口期风险，且 10 用户×每 30s 全量查询的负载与 SSE 心跳相当。

**决策**：SSE 保留。切换轮询是纯增量（前端 useSse 换实现，后端保留失效事件源）。

**影响面**：7.6 全节、nginx 配置、useSse。

**推翻条件**：甲方对「实时」口径确认接受 30s 延迟——前端换轮询实现，半天级。

## D-005｜2026-09-27｜iOS 后台补传不做推送子系统，四件套兜底

**问题**：iOS 无后台执行（Web Push 不能拉起业务 JS），图片补传延迟如何兜。

**论证**：Web Push+setAppBadge+PeriodicBackgroundSync 四件推送组件的到达率链条=「装了主屏+授了通知权+恰好关着 app+有存图」每环衰减；而照片已在 Dexie 持久化（主屏安装豁免 7 天 ITP 清储，WebKit 官方行为）——数据永不丢，仅上传延迟。推送子系统（VAPID 密钥/订阅存储/权限链）复杂度与收益不成比例。

**决策**：四件套兜底=打开即补传+页内角标 N+pagehide「N 张未传完」警示+主屏安装引导；安卓一次性 Background Sync 为主路径。

**影响面**：7.5 触发矩阵、PWA 引导流程。

**推翻条件**：甲方反馈现场常出现「整日不打开 app 且急需照片即时上传」场景——回补 Web Push 为独立增量（不影响既有架构）。

## D-006｜2026-09-27｜二维码生成唯一实现=前端 qrcode 库

**问题**：二维码在录入成功页（离线可用）、打印页、单件重打三处需要，服务端 ZXing 还是前端生成。

**论证**：录入成功页要求离线可用 ⇒ 前端生成是刚需；三处共用同一实现防「码内容」口径分叉；服务端 ZXing 只为打印页多一条服务端路径+一个 Maven 依赖，无独立价值。浏览器打印若个别打印机对不齐，PDF 服务端兜底是半天级纯增量。

**决策**：前端 qrcode 1.5 全站唯一实现；QR 规格（ECC=M/quiet zone≥4/模块≥0.5mm/码边≥14mm/300DPI）固化。

**影响面**：7.7、打印页、录入成功页。

**推翻条件**：甲方特定打印机实测浏览器打印对不齐——加 PDF 兜底端点。

## D-007｜2026-09-27｜运行时配置开关收敛 11→3

**问题**：多轮评审曾累计 11 个 sys_setting 运行时开关（锁定策略/图片鉴权/导出字段/SSE 降级/上传配额等）。

**论证**：开关越多=测试矩阵组合爆炸+「开关永远停在默认值」的死代码越多；逐项评估：滞销 N/M 与标签尺寸有需求明文（保留 admin UI）；CSV 列映射放 yml（格式变更本需发版验证，给非技术甲方的 JSON 编辑框是陷阱）；登录阈值/图片上限无运营调参场景（常量）；其余均砍（需要时均为小改增量）。

**决策**：sys_setting 仅存滞销 N/M+标签尺寸；include_price_code=yml。

**影响面**：5.3、setting 模块、admin UI。

**推翻条件**：甲方提出明确的运行时调参需求——单项加回均为独立小改。

## D-008｜2026-09-27｜MySQL 容器 buffer_pool 384M（非 512M）

**问题**：测试服务器 768M cgroup 限额下 MySQL 内存配置。

**论证**：512M 池+performance_schema 150-300M+基础 RSS 120-180M≈800M-1GB，超 768M 硬限=OOM 重启循环（「零影响隔离」变「零影响但自杀」）；数据集封顶 ~400MB、热集 ~10MB，384M 覆盖 >95% 场景，性能损失≈0；关 performance-schema（无监控抓取链路）。

**决策**：`--performance-schema=OFF` + innodb_buffer_pool_size=384M，常驻 ~550-600M。

**影响面**：deploy compose、压测环境同值。

**推翻条件**：压测 p95 不达标且 profiling 证明瓶颈在 buffer pool——评估单独 MySQL 宿主/升配。

## D-009｜2026-09-27｜对账不变量采用「双向入账」公式

**问题**：ledger 与 item 现状如何自检（TRANSFER 记 0、在途退货、作废三类行在朴素公式下数学不成立）。

**论证**：每行按 (from仓,−move)/(to仓,+move) 双向入账后，每仓 Σ入账 ≡ COUNT(在库未删未废) 对全部 14 类 txn 成立；VOID/回收站删除按库存态钉死记账（在库 −1、在途/已出库 0）。

**决策**：双向入账公式+每日自检 job（按仓聚合首遍扫+命中下钻）+结果落 sys_alert。

**影响面**：LedgerWriter、每日 job、restore --verify 复用。

**推翻条件**：新增 ledger 类型时重新验证公式覆盖（进 code-review 清单）。

## D-010｜2026-09-27｜测试策略采用确定性场景矩阵（弃 jqwik/随机混沌）

**问题**：CSV 合并不变量与并发容错的测试形态——property-based 随机生成还是枚举矩阵。

**论证**：输入空间（状态×价格×时间戳序）可枚举——枚举矩阵失败必可复现；jqwik 随机失败需还原种子、CI flaky 治理成本高；并发混沌（随机 kill 连接/重启容器）同理，Testcontainers 无 restart() 一等 API。

**决策**：CSV 三不变量枚举矩阵；并发容错=DataSource 代理 5 注入点参数化故障注入；容器重启降级为 M7 手动演练留档。

**影响面**：十一节测试表。

**推翻条件**：无（纯测试形态决策，成本已锁定）。

## D-011｜2026-09-27｜「出荷待ち」独立业务入口（不并入对账视图）

**问题**：已成交未出库的商品清单放在哪。

**论证**：雅虎成交→打款→打包发货有数天时滞，这是仓库每天的拣货队列（日课），不是对账异常；埋在 reconcile 命名空间里=每天打开「异常页」干正常活。

**决策**：移动+桌面双入口「出荷待ち」清单（按货架号排序+缩略图+行内扫码卖出）；对账三活视图保留同一差集作滞留监控视角。

**影响面**：六节 API、前端页面。

**推翻条件**：甲方反馈发货时滞实际很短——两视图合并为小改。

## D-012｜2026-09-27｜作废重录前后件互链（re_entry_of 列）

**问题**：作废重录后，扫旧标签如何找到新号（否则盘点时新旧对不上，全靠认照片翻录入记录）。

**影响面**：5.1 DDL、作废流程、扫码提示。

**推翻条件**：无。

**问题**：全局 80% 无 enforcement+核心 70% 的旧口径=最高风险模块拿最低门槛。

**论证**：风险与门槛应同向——itemcode/inventory/yahoo 是账实正确性与并发的所在，行 85%/分支 70%；其余（DTO/entity/config 排除后）BUNDLE 60% 防形式主义；mapper XML 由集成测试承担（口径显式声明）；前端 stores/composables/utils ≥80%（纯 TS 零 DOM，ROI 最高）。

**决策**：JaCoCo 分域门禁（lombok.config 加 @Generated 过滤）+vitest coverage threshold 入 CI。

**影响面**：CI、十节。

**推翻条件**：无。

## D-016｜2026-09-27｜框架锁版 Spring Boot 4.1.1（非 3.5.x）

**问题**：M0 锁版复核发现 3.5 线 OSS 支持 2026-06-30 已结束（末版 3.5.16 后无免费安全补丁）；现行受支持稳定线为 4.1.x（4.1.1），4.0.x 补丁至 2026-12。技术方案原文「≥3.5、M0 锁版终审」触发本决策。

**论证**（版本数据均经 Maven Central 元数据 2026-09-27 实查）：
- 3.5.16：生态最成熟零意外，但已停发 OSS 安全补丁——系统要在甲方生产运行数年，出生即 EOL 是安全 posture 硬伤；Dependabot 无法再提供该线升级流。
- 4.0.8：受支持至 2026-12，仅比 3.5 多 6 个月生命，无意义。
- 4.1.1：受支持至约 2027 年中（与交付节奏匹配）；MyBatis-Plus 已有官方 boot4 starter（mybatis-plus-spring-boot4-starter 3.5.17）、springdoc 3.1.1 支持 Boot 4、Testcontainers 2.0.5 由 Boot BOM 直接托管——迁移成本在空项目时刻≈0，待 17 表+全量代码落地后再迁移才是真成本。风险：Boot 4 配套 Spring Security 7 等 API 变化在 M1 落地时暴露。

**决策**：spring-boot-starter-parent 4.1.1 + mybatis-plus-spring-boot4-starter 3.5.17 + Testcontainers 2.0.5（Boot BOM 托管）+ JaCoCo 0.8.15。

**影响面**：server/pom.xml、M1 Security 配置（按 Security 7 API）、CI。

**推翻条件**：M0 构建或 M1 Security 集成撞上无解的 Boot 4.1 生态不兼容——回退 3.5.16（接受 EOL 姿态+升级依赖监控，M2 前重评）。

## D-017｜2026-09-27｜扩展属性升独立可空列（甲方确认将来启用）

**问题**：甲方答复「将来需要管理商品的详细属性字段」（确认单第 4 项）。技术方案 A6 预案为「确认保留→升独立列」；时机在 V1 尚未部署任何环境的零成本窗口。

**论证**：
- 独立列（现在加）：搜索/导出/排序自然支持（JSON 列筛选能力弱是方案已确认的缺点）；V1 未上线，此刻加列零迁移成本；全部可空=零录入负担。
- 仅 ext_json（等字段清单再升列）：避免猜错字段定义；但「将来要用」已确认，等到有清单时升列=一次加法迁移+导出/搜索/UI 二次接入，成本高于现在。
- 字段来源不靠猜：需求文档已枚举候选（名称/分类/作者窑口/尺寸/重量/渠道），按其落列；清单细化后调整列宽/加列均为加法迁移。

**决策**：item 表新增 item_name/category/author_kiln/size_text/weight_g/sales_channel 六个可空列 + ext_json 保留兜底；录入流程不强制填写；纳入导出（M4）与搜索范围评估（M5）。

**影响面**：V1__init.sql、M4 导出列、M5 搜索范围。

**推翻条件**：甲方提供的最终字段清单与现有列语义冲突（如分类需受控字典而非自由文本）——加列/改造均为有界迁移，无数据损失。

## D-018｜2026-09-27｜容量不做具体件数设计约束（甲方答复）

**问题**：确认单第 5 项「最多 5 万件」口径（活库存 vs 历史累计）。甲方答复「先不要考虑具体件数」。

**论证**：按活库存 5 万件设计的索引/查询本就留余量，无具体上限时该设计自然继续成立；归档机制（已售结清超期数据搬档）为响应「历史累计」口径的预案，甲方未采纳该口径则不实施——避免为不存在的约束引入运维复杂度；阈值告警（item>15 万行/ledger>300 万行）保留作无上限增长的安全网。

**决策**：不按具体件数设定容量约束；归档预案仅保留文档不实现；数据量阈值告警保留。

**影响面**：无需实现改动（原设计即兼容）。

**推翻条件**：实际运营数据量触发阈值告警且影响性能——按预案文档启动归档实现（有界工作量）。

## D-019｜2026-09-27｜本地工作文件忽略策略：仓库级最小化+机器级全局排除

**问题**：初始提交的仓库级 .gitignore 罗列了一批个人本地编辑器/辅助工具文件条目。仓库级忽略清单的职责边界问题。

**论证**：

## D-021｜2026-09-27｜登录走框架 formLogin 过滤器（表单编码），不自研 JSON 认证过滤器

**问题**：SPA 登录请求体格式与认证入口实现的选型：自研 JSON 认证过滤器 vs 复用 UsernamePasswordAuthenticationFilter（formLogin 定制 URL）。

**论证**：
- 自研 JSON 过滤器：请求体任意格式，但要自己处理认证管理器接线、会话固定防护、并发登录控制、事件发布、失败分支——全是框架过滤器链已经打磨过的安全敏感路径，自研即引入审计面。
- 框架 formLogin（`loginProcessingUrl=/api/auth/login`，成功/失败换 JSON 处理器）：changeSessionId、maximumSessions、SessionRegistry、失败计数挂点（AuthenticationFailureHandler）全部原生继承；唯一代价是登录端点用 `application/x-www-form-urlencoded` 而非 JSON——对前端仅是 `new URLSearchParams` 一行差异，且表单编码杜绝 JSON 解析 DoS 面。

**决策**：复用框架 formLogin 过滤器；登录请求表单编码，其余 API 端点照常 JSON。成功/失败/登出/未认证/无权限全部挂自定义 JSON 处理器（LoginJsonHandlers），SPA 无任何 302 跳转。

**影响面**：前端登录请求的 Content-Type；docs/01 六节认证端点契约（方法不变，登录体格式为表单）。

**推翻条件**：若将来要求登录携带更复杂结构（如多租户字段）且表单编码表达不了，再评估自研过滤器。

## D-022｜2026-09-27｜登录锁定：(账号+IP) 内存窗口计数 + 已知账号 DB 锁 + 未知账号内存锁

**问题**：需求「连续输错 5 次锁定 15 分钟」的工程化语义（「连续」无窗口定义；未知账号无行可锁；纯账号维度可被武器化为全员 DoS）。

**论证**：
- 纯账号维度锁 DB：任何攻击者输入任意员工号 5 次即可锁死该员工——把防爆破机制变成 DoS 武器（docs/01 八节已论证，此处落地）。
- (账号+IP) 维度：攻击者换 IP 可重试，但目标场景（内网 10 人 + 公网暴露）下穷举 IP 成本已足够高；跨 IP 攻击信号交给 DB failed_attempts 累计计数（管理员可见）+ 后续渐进延迟。
- 窗口语义：「连续」不设窗口则数月 sporadic 失败也会累计到 5 次误锁正常用户；取「15 分钟窗口内 5 次」——与锁时长一致，误锁概率与爆破难度平衡。
- 未知账号：无 DB 行 → 内存锁（ConcurrentHashMap，(账号+IP) 键）兜底防枚举式撞库；已知账号达阈值写 DB locked_until（跨重启有效、管理端可解锁）后清内存态，判定权移交 DaoAuthenticationProvider 前置检查（锁定期内正确密码也 423）。
- 时序枚举：未知用户名先跑一次 dummy BCrypt 再抛 UsernameNotFoundException，抹平「用户不存在（快）vs 密码错误（慢）」；响应内容层由失败处理器统一字节级相同的 401 JSON。

**决策**：如上组合。常量 MAX_ATTEMPTS=5 / LOCK=15min / WINDOW=15min 收敛在 LoginLockService（需求无运营调参场景，不进 sys_setting）。

**影响面**：LoginLockService/LoginThrottleFilter/KcglUserDetails；管理端「手动解锁」端点在账号管理切片补齐（清 locked_until）。

**推翻条件**：若公网爆破实测出现单账号多 IP 穷举，升级为「同账号跨 IP 累计 N 次全局锁」（DB failed_attempts 已在累计，改动局部）。

## D-024｜2026-09-27｜停用/锁定的即时生效：每请求账号状态校验，而非 SessionRegistry 踢会话

**问题**：管理员停用（或锁定）某账号后，其既有登录会话（最长 12h 滑动）是否继续有效。「停用恶意/离职员工」的业务语义要求立即断权，不能等会话自然过期。

**论证**：
- 不处理（等 12h 过期）：语义缺口——停用通常就是要立刻断，12h 窗口内对方仍可操作全部数据，安全上不可接受。
- SessionRegistry 踢会话（getAllSessions(username).expireNow()）：框架原生、无每请求开销；但①注册依赖 HttpSessionEventPublisher 的容器事件，MockMvc 测试环境不触发，集成测试无法覆盖；②仅本实例内存有效，未来多实例部署即失效；③锁定/停用是 DB 状态，会话踢除与 DB 双写有不一致窗口。
- 每请求主键查库（AccountStatusFilter，挂 SecurityContextHolderFilter 之后）：①按 userId 主键 select <1ms，≤10 用户低频操作下无感知；②DB 为唯一事实源，无一致性窗口；③MockMvc 可测（「停用→既有会话下一请求 401」用例已覆盖）；④多实例天然正确。
- 性能顾虑评估：每认证请求一次额外 SELECT——10 用户×日常操作量远低于 Hikari 16 连接的承载线；且这是"即时权限回收"的通用机制，后续锁定/密码重置等语义同样受益。

**决策**：AccountStatusFilter 每请求校验 enabled + locked_until，命中即清 SecurityContext + 移除会话 context 属性 + 401 统一 JSON。DB 锁定同样即时踢出（管理员手动锁定场景同权回收）。

**影响面**：SecurityConfig（过滤器装配）/AccountStatusFilter；每请求多一次 SELECT（已评估可接受）；后续 SSE 连接随会话失效关闭（7.6 既有设计与此语义对齐）。

**推翻条件**：若用户量/请求量级显著增长（数百用户或高频轮询）导致 DB 压力可测，加 30s 本地缓存（牺牲即时性上限 30s）或切回 SessionRegistry + 事件广播组合。

## D-025｜2026-09-27｜账号管理切片三处伴随修复（404 信封 / 管理员自锁护栏 / MP 分页依赖拆包）

## D-026｜2026-09-27｜审计落地：显式 AuditRecorder 调用，否决 @Audited AOP 声明式方案

**问题**：operation_log 审计的接入方式——规划期构想的 @Audited 注解 + AOP 切面，还是显式 AuditRecorder 调用。

**论证**：
- AOP @Around @Audited：声明式、"标注即审计"的心智保证；但审计的核心价值内容（detail 前后值 diff）在方法内部，切面拿不到——只能靠 SpEL 表达式从参数/返回值提取，每个方法写一遍表达式=比直接写代码更绕；record/Java 对象反射取 id 又一层魔法。声明式的收益（防忘写）远不抵复杂度，且 SpEL 写错是运行期才炸。
- 显式 AuditRecorder.record(...)：detail 精确构造（before 快照在改前取、after 在改后取），一眼可读；缺点是忘写即漏审计——以"每个写端点必须有对应审计用例"的集成测试对冲（AuditIntegrationTest 逐端点断言 operation_log 一行）。
- 事务性：两种方案都要求业务+审计同事务。显式调用直接写在 @Transactional 方法内天然同事务；AOP 还要额外处理切面与事务切面的顺序。

**决策**：显式 AuditRecorder（common/audit）；写方法 @Transactional 包住业务+审计（审计写失败则业务回滚，绝不丢审计）；每写端点一条集成用例断言审计行作为防漏对冲。改密/改语言从 AuthController 下沉 AuthService（controller 无事务，审计原子性纪律要求）。ip 取 X-Forwarded-For 首值 fallback remoteAddr；UA 截 255；detail 与整行严禁密码材料（契约测试断言）。

**影响面**：AuditRecorder/OperationLogEntity/OperationLogMapper/UserService（五写方法）/AuthService（新）+AuthController（瘦身）/AuditIntegrationTest（7 用例）；M2+ 每个业务写端点沿用此模式。

**推翻条件**：若后续出现横切性质的审计需求（如"所有 @Transactional 写方法自动记一行粗粒度日志"），可补充 AOP 做兜底层，与显式 recorder 共存（粗粒度自动 + 细粒度显式）。

## D-028｜2026-09-27｜E2E 冒烟架构：一次性 MySQL 容器 + e2e profile 种子，全栈经 Vite 代理同源访问

**问题**：M1 E2E 冒烟的运行栈怎么搭——复用本地 compose 栈、Testcontainers 拉起、还是独立一次性容器；以及种子数据从哪来。

**论证**：
- 复用本地 compose（kcgl-mysql 常驻库）：零额外启动成本；但 E2E 依赖开发者本机栈状态（上次跑剩的数据、BootstrapAdminRunner 随机密码管理员、被 taro 改过密码的账号），必然 flaky 且不可在 CI 复现；测试污染开发库违反隔离原则。
- Testcontainers（后端集成测试同款）：Java 生态原生；但 Playwright 是 Node 侧进程，webServer 由 Playwright 配置拉起，跨语言拉 Testcontainers 要么走 Java 测试套件要么手写 REST API 驱动，复杂度不成比例。
- **一次性 Docker 容器 + Playwright webServer 启动链**（选定）：`webServer` 双实例——start-backend.mjs 先 `docker rm -f kcgl-e2e-mysql`（幂等）再 `docker run -p 127.0.0.1::3306`（随机宿主端口，`docker port` 发现，杜绝与本地 3306/3307 冲突），`mysqladmin ping` 健康后以 `SPRING_PROFILES_ACTIVE=e2e` 拉起 server/target 的 jar（SERVER_PORT=18080），前端 `npm run dev` 经 `KCGL_API_TARGET` 代理到 18080——浏览器视角全程同源（/api 走 Vite 代理，与生产同源部署拓扑一致）；globalTeardown `docker rm -f` 清场。
- 种子数据两条路：Flyway afterMigrate 回调（进主迁移链，生产也执行，不可接受）或 **e2e profile 的 E2eDataSeeder**（@Profile 隔离，生产无此 profile 永不运行）。选后者。

**决策**：一次性容器栈 + E2eDataSeeder。关键细节四条：
1. **E2eDataSeeder 必须 @Order(0)**：ApplicationRunner 无序时与 BootstrapAdminRunner（空库建随机密码管理员）竞速；Order(0) 保证 seeder 先建好固定密码账号（admin/editor/viewer/taro），BootstrapAdminRunner 见库非空即跳过——否则 E2E 拿不到可预测凭据。

## D-029｜2026-09-27｜三语全量契约 CI 强制 + 文档元数据联动（含 vue-i18n 管道符陷阱）

**问题**：执行期新原则「所有文案都要有日中英三语，切换语言时所有文案都要同步切换」如何落地成机制，而不是靠自觉。

**论证**：
- 现状审计：三语 key 树当前一致、全部视图走 t()（vue-i18n 组合式 API 响应式切换）；但存在两类缺口——①vue-i18n 的 missing-key 是静默回退（渲染 key 本身），未来漏配某语言的 key 页面上看不出来；②document.title 与 <html lang> 是静态值，切换语言不联动（浏览器标签页标题恒日文）。
- 三语齐备的强制层选择：运行时告警（控制台 warn）——CI 不可见，等于没有；@intlify/eslint-plugin-vue-i18n——覆盖模板内 key 引用，但 key 树 parity 与插值参数一致性靠自定义单测更直接；**自定义契约单测**（key 树一致/插值参数一致/非空/渲染一致四断言）零依赖、报错信息可指名道姓，选定。
- 文档元数据联动位置：路由 afterEach 改 title（切语言后不重触发，需 watch locale）；**App.vue watchEffect 同时依赖 locale+route**（语言切换与路由切换都即时生效），路由 meta.titleKey 声明每页标题文案。

**决策**：
1. **契约单测四断言入 CI**（src/i18n/locales.spec.ts）：key 树三语完全一致（以 ja 为基准，多/少都报）/同 key 插值参数集合一致（{minutes} 类）/无空文案/**渲染契约**——每个 key 的 t() 实际渲染与「字面模板直接插值」逐字一致，拦截消息语法被 vue-i18n 特殊解析类缺陷。
2. **渲染契约的由来（实测踩坑）**：标题模板 en 用 "{page} | {app}"（ASCII 管道）时，vue-i18n 把 `|` 解析为复数分支语法，t() 渲染只剩 "Sign in" 静默丢后半；日中全角 ｜（U+FF5C）不受影响。修复=ASCII 管道写字面量 `{'|'}`；契约测试从此把这类静默丢字拦在 CI。
3. **App.vue watchEffect 联动**：`document.documentElement.lang = locale`（无障碍/字体选择跟随）+ 文档标题（子页面「页面名｜系统名」经 common.titleWithPage 插值，分隔符随语言——ja/zh 全角、en 转义 ASCII；首页仅系统名）。路由 meta.titleKey + vue-router RouteMeta 类型增强。
4. LangSwitch 选项文字（日本語/中文/English）为语言自称（endonym），按国际惯例**不随界面语言切换**，视为约定俗成而非文案缺失。

**影响面**：web/src/i18n/locales.spec.ts（新）、locales 三语 titleWithPage、App.vue（watchEffect）、router/index.ts（meta.titleKey+类型增强）、index.html（lang="ja-JP" 与运行时值对齐）、e2e/auth.spec.ts（语言切换断言扩展至标题+lang 属性）；后续每个新命名空间的文案都自动受四断言管辖。

**推翻条件**：若引入 @intlify/eslint-plugin-vue-i18n（规划 M1 备选项）后其规则可覆盖 key 引用面，契约单测保留（覆盖面不同：eslint 管「引用的 key 存在」，单测管「三语树完整+渲染语义」）；若未来确需复数/链接消息语法，对应 key 从渲染契约泛化断言移入显式期望用例。

## D-031｜2026-09-27｜M2-2 管理号引擎：并发取号语义细化（停用会场补录/重放键排他/跳号上限/告警口径）

1. **停用会场仍可补录**：会场停用的语义是「今后不再去该场落札」，不追溯否定历史——次日补录昨日停用会场的落札品是合法路径。引擎只校验会场存在（404003），不校验 enabled；前端下拉只给启用会场，停用场仅补录路径可达。若改为硬禁，跨月补录会被运营节奏变化误伤。

## D-034｜2026-09-27｜M2-5 图片管线：撮影日来源语义、失败二分、幂等路径复用、测试隔离三课

1. **相册照片不默认撮影日、EXIF 自动读取延后**：拍照=撮影日自动=今天（7.5 字面）；相册选图按规格应优先 EXIF DateTimeOriginal，但 exifr 依赖（~50KB）与解码路径属独立增强——先按「不默认」落地（宁缺勿错：默认今天会把补拍旧物全部标错），M2-6 作废重录携带图片后一并评估补齐。撮影日仍可手动选（上限=今天，与后端同口径）。
2. **photoDate 仅在有照片时提交**：无照片的商品提交 photoDate 是语义噪声（DB 落 photo_date 但无图可对应）；photos>0 且用户已选（拍照自动/手选）才进 payload。
3. **上传失败二分：4xx 业务拒绝+507=永久，网络错误+5xx=退避重试**：重试同样字节对 magic/超限/9 图上限/磁盘满无意义（退避到顶也必败），落 failures 由界面呈现防无限退避；网络与 5xx 瞬时故障按 1s→5s→30s→5min 封顶+jitter 重试，online 事件立即清零重试时钟（弱网恢复即冲）。
4. **落盘文件名复用 clientUuid**：其本就是 UUID 形态且全局唯一；重放（响应丢失后）写同一路径同内容=天然幂等，无需二次生成 uuid 的映射关系。
5. **队列监听器在模块加载时注册（非 init）**：online/visibilitychange 挂模块加载，回调幂等（队列空时无操作）——消除「监听是否存在」对 init 调用次序的依赖，测试也无需触发 init 才有事件响应。
6. **相机/相册双隐藏入口**：iOS 上带 `capture` 属性的 input 恒起相机，相册多选必须独立入口；两入口语义差异（撮影日来源）由 source 参数带入。
7. **保存失败时孤儿照片保留 pending_bind**：文字保存失败（网络）照片已落 Dexie 但无 itemId——保留（不删），下一次保存成功 bindItem 统一绑定；用户可用 × 手动放弃。与 7.5 孤儿态语义一致，M2-6 重录场景同一机制复用。
